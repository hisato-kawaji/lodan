# kimi-k3: `reasoning_effort = low` と既定の比較 (2026-09-21)

#78 の受け入れ条件「kimi-k3 で `low` vs 既定の所要時間・正答を記録」の実測。
難易度ラダー 10 タスク × 2 条件 × 1 回、計 20 実行。ハーネスと指標の定義は [README](README.md)。

- 環境: MacBook Air M3、lodan `main` @ `6947ab6`（release ビルド）、Moonshot 公式 API (`--provider kimi`、`kimi-k3`)
- 条件:
  - `temp` — `reasoning_effort` を**送らない**（サーバ既定。Moonshot の既定は `max`）
  - `think-low` — `--reasoning-effort low`
  - どちらも `--temperature 0.2` を付けているが、K3 は temperature が 1 固定なので lodan が警告して落とす（= 実質、差は effort だけ）
- 緩和策（整形再要求・重複抑止・ナッジ）は両条件とも off。全 20 実行で発火 0、タイムアウト 0
- 再現: `CONFIGS="temp think-low" REPEAT=1 MODEL=kimi-k3 PROVIDER=kimi bash docs/eval/ladder/ladder.sh`

## 結論

1. **`low` は受け付けられ、正答は落ちなかった。** 両条件とも 10/10 合格・チェック通過率 100%。
2. **思考は 73% 減ったが、所要時間は合計で 4% しか縮まなかった。**
   思考過程 5,206 → 1,400 文字、completion 6,554 → 5,489 トークン (-16%)、合計 295 → 284 秒。
   このラダーの規模では、時間の大半は思考ではなくツール往復のレイテンシと本文の生成にある。
3. **簡単なタスクでは遅くなったものが無く、難しいタスクでは呼び出し回数が増えて逆に遅くなることがあった。**
   L0 / L1 の 7 タスクは全て同等以下（合計 141 → 113 秒、-20%）。L2 は 1 勝 2 敗で、
   `L2-http` は LLM 呼び出しが 4 → 10 回に増え 41 → 72 秒。考えずに手を動かして、やり直している形。
4. 各条件 1 回なので、**差の向きを見るための観測**であって統計的な比較ではない。特に結論 3 の
   L2 の逆転は 1 回ずつの結果で、ばらつきの範囲かもしれない。

運用上の含意: kimi-k3 を L0〜L1 相当の細かい作業（ファイルの読み書き、小さな修正）に回すなら `low` で
2 割ほど速くなる（1 回ずつの観測）。多段の組み上げでは既定のままの方が手戻りが少ない可能性がある。
`plan_reasoning_effort = "high"` と `reasoning_effort = "low"` の組み合わせ（計画は深く、実行は軽く）が
この結果と相性が良さそうだが、今回は測っていない。

## 参考: ローカルの thinking モデル

ローカルの Ollama (`qwen35-9b-8k`) では、`reasoning_effort = "none"` で thinking が切れ、
単発の質問で completion 71 → 4 トークン・9.5 → 4.2 秒だった（#105 の PR コメント）。
Moonshot は `none` を試していない（`low` が受け付けられる語彙の下限かどうかは未確認）。
