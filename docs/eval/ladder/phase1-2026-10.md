# Phase 1 ablation — 要件台帳 / Write 行数上限 / tool_choice=required (2026-10-11)

#65 Phase 1（A1 / A2 / B1 / B2）をラダーで測った記録。**結論から**:

- **L1 の粒度では 4 条件とも満点**。差は所要時間だけ
- **L2 は実行ごとの分散が条件差より大きい**。同条件を 3〜4 回回すと 2/4〜4/4、5/7〜7/7 と揺れる。
  1 回の結果で「効いた / 効かない」を言ってはいけない
- **A1（`tool_choice = required`）は実機で安定**。チェック通過率が 4 条件で最良（96%）、時間は基準と同等。
  `Finish` 擬似ツールの読み替えが実サーバ（Ollama）でも通ることを確認
- **B1（要件台帳）は精度を変えず時間を +37〜146% 増やす**（タスク別。下の表）。未達は正しく検出して促すが、
  **促しても同じチェックを落とす**（要件は覚えているのに実装が届かない）
- **A2（Write 行数上限）は、発動すると 9B では完走できないことがある**。原因は埋め戻しの Edit が
  自分の骨格に当たらないこと。上限を下げるほど悪化する。**既定 off のままにする**

## 環境

- MacBook Air M3 / 24GB、Ollama、`qwen35-9b-8k`（`qwen3.5:9b` + `num_ctx 8192`）
- lodan `main` @ `2eab15d`（release ビルド）
- 本番 24 実行（4 条件 × L1 3 タスク + L2 3 タスク × 1 回）+ 追試 12 実行（2 条件 × L2 2 タスク × 3 回）
- 時間は `active_ms`（単調時計の実働）。壁時計は 2 実行でマシンの停止により膨らんだので採らない
- **計測中は cargo を一切動かしていない**。並行ビルドを挟むと生成が数倍遅くなり時間が比較不能になる（試走で踏んだ）

## A2 を実際に発動させる（`split40-none`、同条件 3 回）

ラダーの L2 が作るファイルは 51〜77 行なので、**上限 80 では 24 実行すべてで一度も発動しなかった**。
40 に下げて測り直した。

| L2-cli-json | 結果 | 何が起きたか |
|---|---|---|
| #1 | 2/7 | 132 行を拒否 → 40 行の骨格 → Edit ×2 成功 → `old_string not found` ×3 → 未完成で終了（exit 1） |
| #2 | **7/7** | 79 行を拒否 → 骨格 → **Edit 1 回で成功** → Bash で検証 |
| #3 | 2/7（timeout） | **Write を 3 回拒否**（83 → 52 → 76 行。上限を守った骨格を書けない）、Edit 4 回すべて `old_string not found` |

| L2-http | 結果 | 何が起きたか |

| #2 | **4/4** | 1 回拒否 → 骨格 → 不一致なし |
| #3 | 3/4（`sum`） | 1 回拒否 → 骨格 → 不一致なし |

### 害は「埋め戻しの Edit が当たらないこと」と整合する

6 実行とも**上限は発動した**（`write_split_refused`）。そのうえで、runlog の `old_string not found` の
回数と結果がきれいに対応する:

| 実行 | 拒否 | Edit の不一致 | 結果 |
|---|---|---|---|
| L2-cli-json #1 | 1 | 3 | 2/7 |
| L2-cli-json #2 | 1 | **0** | 7/7 |
| L2-cli-json #3 | 3 | 4 | 2/7（timeout） |
| L2-http #1 | 1 | **0** | 3/4（基準と同じ） |
| L2-http #2 | 1 | **0** | 4/4 |
| L2-http #3 | 1 | **0** | 3/4（基準と同じ） |

**不一致が 0 の 4 実行はすべて基準と同等**（7/7, 3/4, 4/4, 3/4）。不一致が 3 回以上あった 2 実行だけが崩れた。
A2 そのものより、**埋め戻しの手段が `old_string` の一致に依存していること**が効いている、と読める。

ただし **n = 6 で、単独要因として切り分けられているのは #1 だけ**。#3 は「拒否 3 回（83 → 52 → 76 行。
上限を守った骨格を書けない）」と「不一致 4 回」が同時に起きていて交絡している。断定ではなく
「このデータと整合する仮説」として扱い、埋め戻しを追記に替えたあとに同条件で測り直して確かめる。

## 次にやること

- **A2 を直す**: 埋め戻しを `old_string` の一致が要らない**追記**（`Write` の `append` か `Append` ツール）にする。
  拒否メッセージで「次の Write は N 行以内」をより強く縛る
- **D1（`[[verify]]`）**: L2-http の失敗は「要件は覚えているのに実装が届かない」形で、満点になるのは
  自分で検証を回した実行だけだった。検証をハーネスが強制するのが次の鍵
- **D2（編集直後の構文チェック）**: A2 の #1 は「未完成品が残って終了」なので、構文チェックで気付ける
- 分散が大きいので、**以後の L2 の比較は同条件 3 回を最低線にする**

## 再現

```bash
# 本番
CONFIGS="think-none req-none split-none required-none" \
TASKS="L1-add-func L1-fix-bug L1-script-run L2-cli-json L2-extend-cli L2-http" \
REPEAT=1 MODEL=qwen35-9b-8k:latest PROVIDER=local T_L0=300 T_L1=480 T_L2=900 \

# 追試 (分散の基準と A2 の発動)
CONFIGS="think-none split40-none" TASKS="L2-cli-json L2-http" REPEAT=3 \

```
