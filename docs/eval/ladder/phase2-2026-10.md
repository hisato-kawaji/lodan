# Phase 2 ablation — 検証ループ / 編集直後の構文チェック (2026-10-11)

#65 Phase 2 の D1 / D2 をラダーで測った記録。Phase 1 は [phase1-2026-10](phase1-2026-10.md)。

**結論**: **D1 / D2 はどちらも毎回走ったが、仕事をする分岐には一度も入らなかった** — 検証は
9 実行すべてで 1 回ずつ走って**毎回成功**（差し戻し 0 回）、構文チェックは 18 回走って**毎回 ok**
（検出 0 件）。9B の失敗は「構文は正しく、プロンプトが明記した実行方法では落ちないが、仕様の解釈を
外す」形で、D1（実行して落ちるか）も D2（構文が壊れているか）も捉える種類ではない。
精度の差は分散。得られたのは「**施策自身のコストは小さく、悪化もしない**」（D2 は 1 回 85ms、
D1 は 1 回 138ms）という事実と、**次に測るべき形**（検証を「実行できる」ではなく「振る舞いを
確かめる」ものにする）。

## 環境

- MacBook Air M3 / 24GB、Ollama、`qwen35-9b-8k`（`qwen3.5:9b` + `num_ctx 8192`）
- lodan `main` @ `a1a5edc`（release ビルド。#149 D1 + #150 D2 を含む）
- **L2 の 3 タスク × 3 条件 × 3 回 = 27 実行**。L0 / L1 は Phase 1 で 4 条件とも満点だったので省いた
- 時間は `active_ms`（単調時計の実働）。壁時計は Phase 1 で 2 回マシンの停止により膨らんだので採らない
- 時間上限は L2 = 1200 秒（検証の差し戻しで往復が増えるぶん、Phase 1 の 900 秒から引き上げた）
- 結果は Phase 2 用に取り直した 27 実行だけ（Phase 1 の結果ファイルとは別。`think-none L2-http` が
  Phase 1 と似た値（LLM 14 回で 4/4）になるのは、**再現した同じパターン**であって流用ではない）
- **計測中は cargo を一切動かしていない**（Phase 1 で、並行ビルドにより生成が数倍遅くなり時間が比較不能になった）

## 条件

| config | = | 足したもの |
|---|---|---|
| `think-none` | 基準 | `--reasoning-effort none`（9B は thinking off が有利） |
| `verify-none` | + D1 | タスクの `VERIFY` を `[[verify]]` として渡す（下記） |
| `syntax-none` | + D2 | `--syntax-check` |

`verify-none` の検証コマンドは、**プロンプトが明記している実行方法だけ**を使う（`checks` の隠し条件は
入れない — それはテストを教えることになる）:

| task | VERIFY |
|---|---|
| L2-cli-json | `python3 scanner.py scan sample` |
| L2-extend-cli | `python3 scanner.py scan sample && python3 scanner.py report sample` |
| L2-http | `python3 -m py_compile server.py` |

ladder は実行ごとの `.lodan/config.toml` に `[[verify]]` として書く（`--verify` をフラグ列で渡すと
空白入りコマンドが単語分割で壊れる。#149 のレビュー）。

## 読み方（Phase 1 から引き継ぐ方法論）

- **L2 は実行ごとの分散が条件差より大きい**。同条件 3 回でも L2-cli-json 5/7〜7/7、L2-http 2/4〜4/4 に
  揺れる（Phase 1 の実測）。n=3 の差で「効いた」と断定しない
- **施策が実際に発火したかを runlog で確認する**。D1 は `verify_run` / `verify_repair` /
  `verify_failed_at_end`、D2 は `syntax_check { ok }`。発火 0 の実行は基準と同一コードパスなので、
  効果の評価対象にしない（Phase 1 の A2 は上限 80 で一度も発火せず、それに気づかず「分散」を
  「悪化」と読みかけた）

### L2-http で時間が 3〜4 倍に見えるのは往復回数の差

基準 186 / 204 秒に対し verify-none 698〜856 秒、syntax-none 259〜696 秒。**施策のコストではなく、
その実行が何回 LLM を呼んだかの差**である:

| config | # | act | LLM 呼び出し | 1 呼び出しあたり |
|---|---|---|---|---|
| think-none | #1 | (未記録) | 14 | — |
| think-none | #2 | 186s | 5 | 37s |
| think-none | #3 | 204s | 6 | 34s |
| verify-none | #1 / #2 / #3 | 698 / 767 / 856s | 14 / 13 / 15 | 50 / 59 / 57s |
| syntax-none | #1 / #2 / #3 | 603 / 696 / 259s | 14 / 14 / 8 | 43 / 50 / 32s |

- 基準の 186 / 204 秒は **LLM 5〜6 回で早々に終えた実行**。基準の #1 は LLM 14 回まで粘って 4/4 を
  取っており、`active_ms` が記録されていればおそらく同じ水準だった (Phase 1 の基準 L2-http は
  LLM 13 回で 644 秒)
- 1 呼び出しあたりでも 34〜37 秒 → 43〜59 秒に伸びている。これは**文脈が長い実行ほど prefill が
  遅くなる**ため (ツール往復が増えるほど履歴が伸びる)。施策自身のコストは runlog で直接測れて
  **D1 が 138ms / 回、D2 が 85ms / 回**で、この差の説明にはならない
- つまり「施策を入れると遅くなる」ではなく「**長く粘った実行は遅い**」。粘ったこと自体は
  D1 / D2 が仕事をした結果ではない (発火の表のとおり、どちらも分岐に入っていない)

### 施策の発火 (runlog の機械集計) — ここが本題

| | 発火 | 結果 |
|---|---|---|
| **D1** `verify_run` | 9 実行すべてで **1 回ずつ** | **9 回とも成功**。`verify_repair` **0 回**、`verify_failed_at_end` **0 回** |
| **D2** `syntax_check` | 18 回 | **全て `ok=true`**。構文エラー検出 **0 件**、`unavailable` 0 件、合計 **1,524 ms** |

**つまり D1 の修復ループも D2 の検出も一度も試されていない。** 表の差 (L2-cli-json で基準 18/21 vs
D1 21/21) について、**差し戻しが 0 回なので「失敗を差し戻して直させる」という D1 の本体は
働いていない**。ただし「基準と完全に同一」ではない: 検証コマンドの実行自体は副作用を持ち得る
(下記の交絡)。したがってこの差は「D1 が効いた」とは読まず、分散 + 副作用の可能性として扱う。

### 見つけた交絡: 検証コマンドの副作用

L2-cli-json の `VERIFY` は `python3 scanner.py scan sample`。これは**実行すると
`state/sample.json` を作る**ので、採点側の `json_created` / `runs_clean` を助け得る。
今回落ちたのは内容の誤り (`field_name` / `field_files` / `field_types`) だったので実害は無かったが、
「検証コマンドが成果物を作る」構成では D1 の効果と採点の助けが分離できない。
**次の ablation では、副作用の無い検証 (読んで確かめるだけ) を使う。**

## なぜ発火しなかったか

9B が書いたコードは、今回の 27 実行すべてで

- **構文は正しい** (D2 が 18 回確かめた)
- **プロンプトが明記した実行方法では落ちない** (D1 が 9 回確かめた)

その上で `field_files` が 6 (自分が作った成果物まで数えた) / `name` が絶対パス / `sum` の仕様違反、
のように**仕様の解釈を外す**。これは「実行して落ちるか」では捉えられない。

## 次にやること

- **検証を「振る舞いの確認」にする**: 利用者が書くのは普通テストで、「起動する」ことではなく
  「期待した値を返す」ことを確かめる。ラダーの `VERIFY` も、プロンプトに書かれた仕様から導ける
  **振る舞いの確認** (出力ファイルの中身を読む、エンドポイントを叩いて返り値を見る) に変える。
  ただし `checks` と同じにしてはいけない (テストを教えることになる) — プロンプトに明記された
  部分だけを使い、副作用を持たない形にする
- D2 は現状「無害だがこのタスク群では仕事が無い」。**構文が壊れる場面** (A2 の埋め戻しで未完成の
  ファイルが残るケース、Edit の連続失敗) と組み合わせて測るのが筋
- Phase 1 の A2 修正 (埋め戻しを追記にする) と合わせて、`split40-none` + `syntax-none` +
  `verify-none` の組で測ると、3 つの施策が噛み合うかが見える
