# Phase 3 ablation — Plan→Execute 分離 (2026-10-12)

#65 Phase 3 の C1 をラダーで測った記録。Phase 1 は [phase1-2026-10](phase1-2026-10.md)、Phase 2 は
[phase2-2026-10](phase2-2026-10.md)。

**結論**: **C1 は動くが、このラダーでは便益を測れない。費用は測れている**。理由は 2 つ。
(1) **9B の計画器がほとんど分解しない** — 9 実行中 3〜4 回だけ（残りは「手順 1 つ」と返し、計画の
1 回だけ余分に払って、あとは基準と同じ経路で走る）。(2) 分解したときは**正答が基準と同じで、時間が 1.5〜3.7 倍**。
増えたぶんの大半は手順ではなく、**手順のあとに親が走る検算**（基準 4 回に対し 7〜14 回）。
C1 を測るには、**基準が文脈の積み上がりで実際に劣化する粒度**（複数ファイル・複数段の L3）が要る。
これは Phase 0 の結論（粒度を L0-L2 に落とせば 9B は現行 lodan で 8/10 通る）の裏返しで、
**今のラダーは C1 にとって簡単すぎる**。

## 環境

- MacBook Air M3 / 24GB、Ollama、`qwen35-9b-8k`（`qwen3.5:9b` + `num_ctx 8192`）
- **L2 の 3 タスク × 2 条件 × 3 回 = 18 実行**を 2 回（round 1 / round 2）。L0 / L1 は依頼が
  80 文字未満で分解の対象にならない（= 基準と同一）ので省いた
- 時間は `active_ms`（単調時計の実働）。壁時計は採らない（round 1 で 4 実行がスリープを挟んだ）
- 時間上限は L2 = 1800 秒（手順ごとに往復が増えるぶん、Phase 2 の 1200 秒から引き上げた）
- **計測中は cargo を一切動かしていない**（Phase 1 で、並行ビルドにより生成が数倍遅くなった）

| | lodan | 条件 |
|---|---|---|
| round 1 | main `8539dfe`（#154 のまま） | `think-none` / `plan-none` |
| round 2 | `1a25890`（#156: 手順の反復予算を親と同じに + 計画プロンプトに分解の目安） | 同じ |

`plan-none` = `think-none` + `--plan-execute`。

## 読み方（Phase 1/2 から引き継ぐ方法論）

- **施策が発火したかを runlog で確認してから解釈する**。C1 は `plan_made` / `plan_step` /
  `plan_skipped`。`plan_skipped` の実行は計画の 1 回（512〜733 tok）だけ余分で、あとは基準と同じ経路なので、
  効果の評価対象にしない
- **L2 は実行ごとの分散が条件差より大きい**。n=3 の差で「効いた」と断定しない
- **round をまたいだ集計を比べない**（下の round 2 を参照。基準そのものが動いた）
- **`metrics.llm_calls` は親だけ**を数える。子の呼び出しは `result.json` の
  `usage.by_kind.subagent` に出る（下の表では分けて書いた）

## round 1 (18 実行) — 測れたのは「手順の実行予算が足りない」こと

| | pass | checks | 中央値 秒 |
|---|---|---|---|
| `plan-none` | 22% (2/9) | 73% | 163 |
| `think-none` | 56% (5/9) | 81% | 120 |

発火の内訳が本題:

| | 回数 |
|---|---|
| `plan_made`（分解された） | **4 / 9** |
| `plan_skipped { no_plan, steps: 1 }` | 5 / 9 |
| 分解された実行のうち**手順が落ちた** | **3 / 4** |

落ちた理由は 3 件すべて同じで、`plan_step.ms` は **380,632 / 387,706 / 475,025 ms**:

```
[lodan] step 2/3 failed: tool error: sub-agent hit max_iterations (12) without a final answer
```

`SUBAGENT_MAX_ITERATIONS = 12` は「静かに走る調査の子がコストを焼かない」ための上限で、
**手順はそのターンの仕事そのもの**なので前提が違っていた。1 手順に 6〜8 分使って上限に当たり、
残りの手順を飛ばして親に戻る → 当然に悪化する。**この数字は C1 の評価ではなく実装の欠陥の記録**。

→ #156 で手順を親と同じ `agent.max_iterations`（既定 25）で回すようにし、あわせて
計画プロンプトに分解の目安（「複数のファイル / サブコマンド / エンドポイントを指しているなら
1 つずつに割る」）を足して round 2 を取り直した。1 ターンの子の往復は最悪 `6 × 25 = 150`（従来 72）まで
伸びる。`max_requests` / `max_total_tokens` は既定で無制限なので、既定で効く歯止めは手順数の上限 6 だけ。

## round 2 (18 実行) — 予算の欠陥は消えたが、効果は出ない

| | pass | checks | 中央値 秒 |
|---|---|---|---|
| `plan-none` | 56% (5/9) | 85% | 180 |
| `think-none` | 67% (6/9) | 90% | 164 |

**この差は読めない** — 9 実行のうち 6 は `plan_skipped { no_plan }` で、計画の 1 回のほかは基準と同じ経路だから。

**round 1 の表と比べない**。両方の変更の影響を受けない `think-none` が、中央値 120 → 164 秒、
L2-cli-json では 98 / 85 / 119 → 469 / 310 / 328 秒（3〜4 倍）と round 間で動いた。`plan-none` の
`22% → 56%` を修正の効果と読まないこと。修正を支持するのは下の**手順の失敗 3 → 0** の方。

もう 1 つ、round 1 → 2 では**予算と計画プロンプトの 2 つを同時に変えた**ので、どちらの効果かは
実測では分離できない。以下の帰属（分解率は計画プロンプト、手順の失敗は予算）は、予算が計画の判断より
後にしか効かないことからの推論。

| | round 1 | round 2 |
|---|---|---|
| `plan_made` | 4 / 9 | **3 / 9**（L2-extend-cli のみ、各 2 手順） |
| 手順の失敗 | 3 | **0** |
| `plan_skipped { no_plan }` | 5 | 6 |

**分解の目安を足しても分解率は上がらなかった**（4/9 → 3/9、分散の範囲）。L2-http は 2 つの
エンドポイントを名指ししているので規則に当てはまるのに、3 回とも「手順 1 つ」と返している。
**計画器が 9B である限り、分解するかどうかは安定しない**。

### 分解された実行だけを比べる (L2-extend-cli ×3)

| config | checks | active 秒 | 親の LLM | 子の LLM | 計画の LLM |
|---|---|---|---|---|---|
| `plan-none` #1 | 5/5 | 434 | 12 | 5 | 1 (591 tok) |
| `plan-none` #2 | 5/5 | 408 | 14 | 8 | 1 (563 tok) |
| `plan-none` #3 | 5/5 | 170 | 7 | 7 | 1 (549 tok) |
| `think-none` #1-3 | 5/5, 5/5, 5/5 | 117, 116, 112 | 4, 4, 4 | — | — |

- **正答は同じ**（どちらも 3/3 で満点）
- **時間は 1.5〜3.7 倍**
- 計画そのものは安い（1 回・約 570 トークン）
- **増えたぶんの主役は親**。基準の 4 回に対し 7〜14 回回っている

### 親が何をしているか (`plan-none` #2 の実測)

```
plan_made steps=2
  plan_step 1/2 ok  27s
  plan_step 2/2 ok 236s
  tool Read ok / Bash error / Edit ok / Bash error / Bash ok / Bash ok / Bash error
     / Bash ok / Bash error / Bash error / Bash ok / Bash ok / Read ok
```

手順が終わったあと、親が 13 回のツール呼び出し（Bash の失敗 5 回を含む）で**検算と手直し**を
している。注記が「読んで、走らせて、利用者に答えろ」と頼んでいるので**仕様どおり**だが、
結果として「子が作る → 親がもう一度確かめる」の二重払いになっている。
C1 の狙いは親の文脈を短く保つことなのに、親の呼び出し回数は基準より増えた。

## 費用: 測れている

分解された 3 実行は L2-extend-cli の 3 回で重複が無く、3 回とも同じ向きに出ている。

- 時間は基準の **1.5〜3.7 倍**（active 170〜434 秒 対 112〜117 秒）
- 親のトークンは **14.1k → 27.9〜66.0k**。増えたぶんの主役は手順ではなく、手順のあとの親の検算
- 計画は 1 回・約 570 トークンで、費用の中では小さい

## 便益: なぜ測れないか

- L2 の 3 タスクは **1〜2 ファイル・1〜2 コマンド**。基準でも親の LLM 呼び出しは 4〜10 回で、
  文脈が積み上がって終盤に崩れる前に終わる。**分解で捨てられる文脈がそもそも無い**
- 失敗の形は Phase 2 と同じ「構文は正しく実行も通るが仕様が違う」(`field_name` が絶対パス、
  `sum` の仕様違反)。手順に割っても、各手順の中で同じ誤読をする
- 分解の質は**計画器のモデル**に依存する。9B は「1 手順」を選びがちで、割った場合も
  「scan を書く / report を足す」のように**元の依頼の文そのまま**で、取り違えを防ぐ情報が増えない

## 次にやること

- **L3 を作る**（C1 を測れる粒度）: 4〜6 ファイル・2〜3 段の積み上げ（先の段の成果物を後の段が
  使う）で、**基準が文脈長で実際に劣化する**ことを先に確認してから C1 を足す。今のラダーは
  Phase 0 の結論どおり「9B が通る粒度」に落としてあるので、C1 の土俵ではない
- **検算を親からハーネスに移す**: 注記で「読んで走らせて確かめろ」と頼むのをやめ、
  D1 (`[[verify]]`) に 1 回やらせて、失敗だけ親に差し戻す。round 2 の実測では、増えた時間の
  大半が親の検算なので、ここが一番効く見込み
- **計画器だけ別モデルにする**（`.lodan/agents/plan-step.md` の逆: 計画を大きいモデルに投げる）。
  分解するかどうかが安定しないのは計画器の性能の問題なので、そこだけ切り離して測る
