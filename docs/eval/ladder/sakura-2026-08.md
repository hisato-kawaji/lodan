# 難易度ラダー — さくらのAI Engine (2026-08-09)

API 級モデル 2 種 × 4 config × 10 タスク × 3 反復 = **240 実行**。
ハーネスと指標の定義は [README](README.md)、ローカル 3 モデルの結果は
[ベースライン](baseline-2026-07.md)。

- provider: `sakura` (`https://api.ai.sakura.ad.jp/v1`, OpenAI 互換)
- モデル: `gpt-oss-120b` / `preview/Qwen3.6-35B-A3B`
- 実行時間上限は既定のまま (L0/L1/L2 = 120/240/480s)。API 経由では中央値
  3-7s で、上限が律速になった実行は無い
- 消費 **1189 リクエスト** (無料枠 3000 の 40%)、prompt 3.35M / completion 0.23M トークン

## 結論

1. **さくらのAI Engine は lodan からそのまま使える。** tool calling・SSE
   ストリーミング・`tool` ロールの往復・`stream_options.include_usage` まで
   OpenAI 互換で通る。専用の分岐は要らず、`sakana.rs` と同型のアダプタで足りた。
2. **L0-L2 はこのクラスには易しすぎる。** `gpt-oss-120b` は緩和策を全て切った
   `base` で **120 実行中 L0-L2 すべて 100%**。`Qwen3.6-35B-A3B` も L0/L1 は
   ほぼ天井で、割れるのは L2 の 1 タスクだけ。**このラダーでは API 級の
   break point を測れない**ので、比較用の参照値としてのみ使える。
3. **最大の失敗モードはモデルではなくタスク設計の欠陥だった。** 全 240 実行の
   非 pass 14 件のうち、落ちたチェックは `field_files` 11 件 / `field_types`
   10 件に集中している。原因は後述のとおり**フィクスチャ汚染**で、能力の
   指標になっていない。これを除くと両モデルとも実質天井。
4. **`finish_nudge` (#63) はここでも有害寄り**だが、害の出方がローカルと違う。
   `gpt-oss-120b` で 100% → 90%。ローカルでは「LLM 往復が増えて timeout 量産」
   として現れたが、API では timeout 0 のまま**要件の取りこぼし**として出る。
   一方 `Qwen3.6-35B-A3B` では無害 (pass 93%、チェック通過率は 96% で 4 config 中最良)。
5. **#61 の 2 策は 240 実行でも実質不発。** `malformed_retries` は **0 件**、
   `dup_suppressed` は 2 件のみ。ローカル 90 実行で 0 発火だった傾向が、
   API 級でもそのまま続く。この粒度では整形破綻が起きていない。
6. **反復上限に達したのは 1 件だけ** (`gpt-oss-120b/nudge/L2-http/2`、25 呼び出し)。
   これも `nudge` 有効時のみで、律速は反復回数ではない。

## 失敗の内訳 — `field_files` / `field_types` は測定ミス

`L2-cli-json` は「`sample/` を走査して `state/sample.json` を書く CLI」を
作らせ、**`files == 4`**、**`types == ["json","md","py"]`** を assert する。
ところが依頼文は「`python3 scanner.py scan sample` で動くこと」と書いており、
モデルは**自分の実装を検証するために `sample/` へテスト用ファイルを足す**。

実際に落ちた実行の出力:

```
gpt-oss-120b/nudge/L2-cli-json/2 → {"files": 7, "types": ["json","md","py","txt"]}
  sample/ の中身: README.md data.json file1.txt main.py sub/ util.py

qwen3.6-35b-a3b/base/L2-cli-json/1 → {"files": 6, "types": ["json","md","py","txt"]}
  sample/ の中身: README.md data.json file1.py main.py sub/ util.py
```

スキャナは**汚染後の `sample/` を正しく数えている**。つまりこの 2 チェックは
「自己検証をしないモデル」を高く評価する。ラダー README は「否定条件は対象が
存在しないだけで通る」と部分点の**水増し**を戒めているが、これはその逆向きの
失敗 — 正しい実装が**減点**される。

**修正案** (このレポートでは未適用):
`checks` を汚染後の実ディレクトリに対して期待値を計算するか、判定用に
`sample/` の複製を pristine のまま別名で用意する。
今回適用しなかったのは、チェック内容を変えると
[2026-07 のローカルベースライン](baseline-2026-07.md)と数字が比較できなくなるため。
ラダーを再較正するタイミングで両者まとめて取り直すのが良い。

## 計測上の注意

- **1 実行を集計から除外すべき**: `qwen3.6-35b-a3b/mitig/L2-cli-json/1` の
  `fail (0/7)` は実行中にマシンがスリープし SSE 接続が切れたもの
  (`error: SSE chunk error: Transport error`、壁時計 3361s に対し `active_ms=0`、
  `exit_code=0`)。能力の判定材料にならない。除外すると当該セル (qwen/mitig/L2) は
  78% → 88%。以降の実行は `caffeinate -is -w <pid>` を当てて再発を防いだ
- 壁時計 `secs` と `metrics.active_ms` が乖離した実行が他に 3 件ある
  (1609s/501s/62s に対し実作業 0-34s)。いずれも pass なので結果には影響しないが、
  **秒数は `active_ms` を見ること** (README の既知事項)

## 付随して直した設定バグ

この検証の最初の 3 実行は**全て 0 リクエストで即失敗**した。ハーネスが作業 cwd に
書く `.lodan/config.toml` が

```toml
[llm.sakura]
timeout_secs = 900
```

という部分指定で、`ProviderConfig` の serde 既定が全スロット `default_local()`
だったため、**`base_url` が `http://localhost:11434/v1` に巻き戻っていた**
(リモート provider が黙ってローカルの ollama を叩く)。

`[llm.sakana]` でも同じことが起きるので、README が参照実装として載せている
sakana のラダー実行も、この経路では成立していなかったはず。
`ProviderOverlay` を入れて、部分指定でも**そのプロバイダの**既定が残るようにした
(`src/config.rs`、回帰テスト 2 件)。

中央値の所要が 3s → 7s に伸びる。

回すときは実測平均 (5) ではなく最悪値で見積もるか、config 単位でチャンクして
実測を集計しながら進めること (今回は後者、上限 2700 で運用)。
